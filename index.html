01 · لماذا نحتاج إلى مبادئ؟

الثغرات تتغيّر… والمبادئ تبقى

قائمة الثغرات تتغيّر باستمرار، ولا يستطيع المبرمج حفظ حلٍّ منفصل لكل مشكلة. لذلك نحتاج قواعد تصميم عامة تُطبَّق في كل قرار برمجي، فتمنع فئات كاملة من الثغرات بدل ثغرة واحدة.

توجّه القرار التصميمي

تمنح المبرمج معيارًا واضحًا للاختيار بين أكثر من طريقة لتنفيذ الميزة نفسها.

تمنع عائلات من الثغرات

بدل علاج ثغرة واحدة بعد ظهورها، نقلّل احتمال وقوع عائلة كاملة من الأخطاء من البداية.

صالحة عبر الأنظمة

تُطبَّق على تطبيقات الويب والخوادم وقواعد البيانات وغيرها، مهما اختلفت التقنيات.

الفكرة الأساسية: الأمن ليس إضافة نضعها في نهاية المشروع؛ بل طريقة تفكير تبدأ من التصميم وتستمر حتى التشغيل. وتمثّل هذه المبادئ الركيزة الثالثة عند McGraw (2006): المعرفة.
02 · التصميم الآمن · 1975

مبادئ Saltzer & Schroeder الثمانية

ورقة «The Protection of Information in Computer Systems» عام 1975، وما زالت أساسًا في تعليم أمن البرمجيات بعد خمسة عقود.

01 · ECONOMY

اقتصاد الآلية

اجعل آلية الحماية صغيرة وبسيطة. مثال: مكتبة مصادقة واحدة موثوقة بدل تكرار منطق الدخول في كل صفحة.

02 · FAIL-SAFE

الافتراضات الآمنة

المنع هو الأصل، والإذن استثناء صريح. المستخدم الجديد لا يحصل على صلاحيات حتى تُمنح له.

03 · MEDIATION

الوساطة الكاملة

افحص الصلاحية عند كل وصول، لا عند تسجيل الدخول فقط. من يعرف رابط الحذف المباشر يستطيع تجاوزه إن غاب الفحص.

04 · OPEN DESIGN

التصميم المفتوح

لا يعتمد الأمن على سرية التصميم؛ بل على حماية المفاتيح والأسرار وإعدادات الوصول.

05 · SEPARATION

فصل الامتيازات

اطلب أكثر من شرط مستقل للعملية الحساسة: مصادقة متعددة العوامل، أو موافقة شخصين على تحويل كبير.

06 · LEAST PRIVILEGE

أقل امتياز

امنح كل مكوّن أقل صلاحيات يحتاجها فقط. حساب قاعدة بيانات للتطبيق يقرأ ويكتب جداوله فقط.

07 · ISOLATION

أقل آلية مشتركة

قلّل الموارد المشتركة بين المستخدمين؛ مثل عزل بيانات كل عميل في التطبيقات متعددة المستأجرين.

08 · USABILITY

القبول النفسي

الضوابط الأمنية يجب أن تكون سهلة الاستخدام؛ فالضابط المعقّد يدفع المستخدمين إلى الالتفاف عليه.

أضاف المؤلفان مبدآن وصفاهما بأنهما أقل انطباقًا على أنظمة الحاسوب: عامل الجهد (Work Factor) — مقارنة تكلفة كسر الآلية بموارد المهاجم، وتسجيل الاختراق (Compromise Recording) — إذ قد يكفي تسجيل الاختراق أحيانًا بدل منعه.

03 · مبادئ معمارية مكمّلة

ثلاثة اتجاهات تجعل النظام أكثر صمودًا

الدفاع المتعدد الطبقات · Defense in Depth

لا يُعتمد على ضابط واحد، بل تُرتّب طبقات مستقلة، فإن فشلت طبقة بقيت الأخرى. في تطبيق ويب: التحقق من المدخلات طبقة، والاستعلامات المهيأة طبقة، وصلاحيات قاعدة البيانات طبقة ثالثة.

السياسات والتدريب
الشبكة: جدار ناري وفحص
الخادم: إعدادات آمنة وترقيع
التطبيق: تحقق وتفويض وترميز
البيانات

تقليص سطح الهجوم · Attack Surface Reduction

كل واجهة أو خاصية أو منفذ إضافي هو فرصة إضافية للمهاجم. لذلك تُزال الخصائص غير المستخدمة، وتُغلق الواجهات الإدارية عن الوصول العام، ويُقيَّد ما يصل إلى الإنترنت.

الواجهات المقطوعة (بالأحمر) هي الخصائص المزالة أو المُقفلة. أقل وظائف مكشوفة = فرص أقل للاستغلال.

الأمان افتراضيًا · Secure by Default

الإعداد الذي تُشحن به البرمجية هو الإعداد الآمن، دون مطالبة المستخدم بخطوات إضافية: التشفير مفعّل، ووضع التصحيح معطّل، ولا كلمة مرور افتراضية ثابتة.

تشفير مفعّل Debug = off لا أسرار ثابتة مرتبط بـ OWASP A02
04 · المدخلات غير الموثوقة

التحقق من المدخلات: بوابة الثقة

كل ما يعبر حدود الثقة يُعامَل على أنه غير موثوق. نفحصه قبل استخدامه، والتحقق يكون على الخادم دائمًا؛ ففحص المتصفح وحده يتجاوزه المهاجم بإرسال الطلب مباشرة.

التحقق النحوي · Syntactic

هل الشكل صحيح؟ النوع والطول والنمط. مثال: اسم مستخدم من 3 إلى 20 حرفًا بأحرف صغيرة وأرقام وشرطة سفلية.

التحقق الدلالي · Semantic

هل القيمة منطقية في سياقها؟ مثال: تاريخ البداية يسبق تاريخ النهاية، والكمية موجبة.

التوحيد قبل التحقق · Canonicalization

حوّل المدخل إلى صيغة قياسية واحدة قبل الفحص، لأن القيمة نفسها قد تصل بترميزات أو أشكال مختلفة.

مبدأ عملي: ارفض المدخل غير الصالح مبكرًا قبل أن يصل إلى منطق العمل، ثم رمّز المخرج عند إرساله إلى وجهته.
05 · تطبيق عملي

قائمة السماح أم قائمة المنع؟

✓ ALLOWLIST · الأسلوب المفضّل

حدّد المقبول بوضوح

نقبل فقط ما يطابق قواعد معروفة، ونرفض كل ما عدا ذلك. نطاق القيم المقبولة محدَّد صراحةً، لذا يصعب تجاوزه.

# Secure: allowlist validation (Python) import re USERNAME = re.compile(r"^[a-z0-9_]{3,20}$") def validate_username(value: str) -> str: value = value.strip().lower() # canonicalize if not USERNAME.fullmatch(value): # syntactic check raise ValueError("invalid username") return value

مثال: الرمز البريدي = خمسة أرقام فقط.

✕ DENYLIST · لا تكفي وحدها

حاول حظر المعروف فقط

تُحدَّد القيم الممنوعة ويُقبل ما عداها؛ وقد يتجاوزها المهاجم بصيغة أو ترميز لم تتوقعه القائمة.

# Insecure: denylist BAD_WORDS = ["select", "drop", "--"] def validate(value: str) -> bool: for word in BAD_WORDS: if word in value.lower(): return False return True # يقبل أي شيء آخر

قد تكون طبقة إضافية، لكنها ليست بديلًا عن التحقق الصارم.

تنبيه مهم: التحقق من المدخلات لا يغني عن ترميز المخرجات (Output Encoding). بعض المدخلات الصحيحة تمامًا تحتوي رموزًا خاصة (مثل فاصلة عليا في اسم عائلة)؛ وعند عرضها داخل HTML أو استعلام أو أمر، يجب ترميزها حسب قواعد ذلك السياق حتى تُعامَل كبيانات لا كأوامر.
06 · معالجة الأخطاء · OWASP A10 / A09

عند حدوث خطأ أمني، ارفض بأمان

إذا فشل فحص أمني، يجب ألا يتحوّل الخطأ إلى سماح غير مقصود. النتيجة الافتراضية عند الفشل هي الرفض.

✕ INSECURE · FAILS OPEN
# Insecure: fails open def can_delete(user, record_id): try: return db.is_owner(user.id, record_id) except Exception: pass # error swallowed return True # access granted on error

ابتلاع الاستثناء ثم إرجاع True قد يسمح بحذف سجل دون التأكد من ملكيته. التقاط استثناء وتجاهله يخفي المشكلة ويترك النظام في حالة غير معروفة.

✓ SECURE · FAILS SECURELY
# Secure: fails securely and logs import logging, uuid log = logging.getLogger("app.security") def can_delete(user, record_id): try: return db.is_owner(user.id, record_id) except DatabaseError: incident = uuid.uuid4().hex[:8] log.error("ownership check failed incident=%s user=%s", incident, user.id) return False # deny on error

الرفض هو الافتراضي، وتُسجَّل تفاصيل الحادثة داخليًا مع معرّف يربط رسالة المستخدم بالسجل.

رسالة عامة للمستخدم

لا تكشف نص الاستعلام ولا مسارات الملفات ولا Stack Trace.

سجل داخلي مفيد

سجّل محاولات الدخول، ورفض الوصول، وتغيير الصلاحيات، والأخطاء المتكررة — مع الوقت والمصدر ومعرّف الحادثة.

لا تسجّل الأسرار

لا تسجّل كلمات المرور أو رموز الجلسات أو أرقام البطاقات أو البيانات الشخصية الحساسة.

07 · كلمات المرور والأسرار

لا تخزّن ما لا تريد أن يتسرّب

لا تُخزَّن كلمة المرور أبدًا كنص صريح، ولا تُشفَّر تشفيرًا قابلًا للعكس؛ فالطريقة الصحيحة هي التجزئة (Hashing) بملح عشوائي فريد لكل مستخدم، بدالة بطيئة عمدًا.

كلمة المرورسر المستخدم
←
ملح عشوائيSalt فريد لكل مستخدم
←
دالة تجزئة بطيئةArgon2id / scrypt / bcrypt
←
تخزين الناتجالملح + الناتج فقط

الخوارزمية المناسبة

توصي ورقة OWASP بـ Argon2id أولًا، ثم scrypt أو bcrypt، ثم PBKDF2 عند الحاجة للمعايير. أما MD5 وSHA-1 وSHA-256 فهي سريعة جدًا وغير مناسبة وحدها لكلمات المرور.

الملح ومعامل التكلفة

الملح يجعل تجزئات كلمتين متطابقتين مختلفة، ويُبطل جداول القيم المحسوبة مسبقًا. أما الدالة البطيئة ومعامل التكلفة فيرفعان تكلفة تجربة ملايين التخمينات على المهاجم.

ما يجب تجنّبه

لا نص صريح، ولا تشفير قابل للعكس، ولا تجزئة سريعة عامة (MD5 / SHA-1 / SHA-256)، ولا ملح ثابت مشترك بين كل المستخدمين.

الخلاصة: تجزئة + ملح فريد + دالة بطيئة = تخزين آمن. وأي تسريب لقاعدة البيانات لا يكشف كلمات المرور الأصلية مباشرة.
08 · إدارة الأسرار · CWE-798

الأسرار لا تُكتب داخل الشيفرة

كتابة كلمة مرور قاعدة البيانات أو مفتاح API مباشرةً في الشيفرة يعني انتقاله إلى كل من يصل إلى المستودع ونسخه الاحتياطية.

✕ HARD-CODED · CWE-798
# Insecure DB_PASSWORD = "secret-value" API_KEY = "sk-live-abc123..."

أي شخص لديه وصول للمستودع — أو لنسخة احتياطية قديمة — يملك السر.

✓ EXTERNALIZED
# Secure: outside the code import os DB_PASSWORD = os.environ["DB_PASSWORD"] API_KEY = os.environ["API_KEY"]

متغيرات البيئة أو خدمة مخصّصة لإدارة الأسرار، مع تدوير دوري.

خارج الشيفرة

متغيرات البيئة أو خدمة إدارة أسرار مخصّصة.

لا ترفع ملفات الإعداد

ملفات تحتوي أسرارًا لا تُرفع إلى نظام التحكم في الإصدارات.

أقل صلاحية لكل سر

كل مفتاح يُمنح أقل صلاحيات ممكنة، ولا يُعاد استخدامه في أكثر من سياق.

تدوير فوري

يُغيَّر السر دوريًا، وفورًا عند أي اشتباه في تسرّبه.

09 · نمذجة التهديدات · Shostack (2014)

فكّر في الهجوم قبل كتابة الشيفرة

نشاط منظّم في مرحلة التصميم، يكشف عيوب التصميم التي لا تكشفها أدوات فحص الشيفرة. يعتمد على أربعة أسئلة، ثم على نموذج STRIDE لتصنيف التهديدات.

S · Spoofingطالب يسجّل باسم زميله.مصادقة بحساب جامعي وجلسة آمنة.
T · Tamperingتعديل رقم الشعبة في الطلب لتجاوز السعة القصوى.فحص السعة في الخادم لا في الواجهة فقط.

11 · ربط المفاهيم

من المبادئ إلى مخاطر OWASP Top 10

المبادئ ليست نظرية منفصلة؛ بل ترتبط بفئات مخاطر معروفة وتوجّه قرارات التنفيذ والمراجعة.

A01

التحكم في الوصول — الوساطة الكاملة، أقل امتياز، الافتراضات الآمنة.

A02

الإعدادات الخاطئة — الأمان افتراضيًا، تقليص سطح الهجوم.

A05

الحقن — التحقق من المدخلات، ترميز المخرجات.

A04 / A07

التشفير والمصادقة — تخزين كلمات المرور بطريقة صحيحة، إدارة الأسرار.

A06

التصميم غير الآمن — نمذجة التهديدات، اقتصاد الآلية.

A09 / A10

التسجيل والحالات الاستثنائية — الفشل الآمن، التسجيل والتنبيه دون كشف بيانات حساسة.

المبادئ العامة تمنع فئات كاملة من الثغرات، وليست حلًا لثغرة واحدة بعينها.
الخلاصة · أهم ما نخرج به

الأمن يبدأ من قرار صغير

١. صمّم على أساس المنع

افحص الصلاحية عند كل وصول، وامنح أقل امتياز لازم، واعتمد الافتراضات الآمنة.

٢. افحص كل مدخل

استخدم قائمة سماح، وتحقّق على الخادم دائمًا، ولا تنسَ ترميز المخرجات.

٣. افشل بأمان

ارفض عند تعذّر الفحص، واكشف للمستخدم رسالة عامة فقط، وسجّل التفاصيل داخليًا.

٤. احمِ الأسرار

جزّئ كلمات المرور بدالة بطيئة مع ملح فريد، وأبقِ المفاتيح خارج الشيفرة.
